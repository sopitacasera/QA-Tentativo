2. Diseño de la prueba

Los cinco casos corren en orden y comparten el mismo id. No se pueden
reordenar: la consulta y la actualización dependen del alta.

CP-01. Alta. Positivo.
Entrada: id aleatorio de 9 dígitos, nombre Mascota-{id}, una URL de foto
y estado available. photoUrls va en el cuerpo porque el contrato lo exige.
Esperado: HTTP 200 y el mismo id, nombre y estado.
Obtenido: passed. 677 ms. El id devuelto fue 147028996.

CP-02. Consulta por id. Positivo.
Esperado: la mascota recién creada, todavía available.
Obtenido: passed. 109 ms. Nombre Mascota-147028996 y estado available.

CP-03. Actualización. Positivo.
Entrada: el mismo id, nombre Mascota-vendida-{id}, estado sold.
Esperado: HTTP 200 en el PUT y, al leer de nuevo por id, el nombre nuevo
y el estado sold. La segunda lectura evita dar por bueno un PUT que solo
devuelve lo que se le envió.
Obtenido: passed. La lectura posterior confirmó nombre y estado sold.

CP-04. Búsqueda por estado. Positivo.
Esperado: la lista de estado sold incluye esa mascota, con el nombre nuevo.
Obtenido: passed al primer intento. 328 ms. La lista traía 417 mascotas
y la nuestra estaba entre ellas.

CP-05. Id inexistente. Negativo.
Esperado: HTTP 404 y un mensaje de mascota no encontrada. No crea datos.
Obtenido: passed. 109 ms. Cuerpo: code 1, type error, message "Pet not found".

Al cierre, un DELETE borra la mascota de esta corrida. La demo es

3. Qué se vio en la API

OBS-01. El cliente manda el id.
La demo acepta el id en el POST y lo guarda tal cual. Dos personas pueden
elegir el mismo número y pisarse la mascota. Por eso esta suite usa un
aleatorio de 9 dígitos. En una tienda real el id debería generarlo el
servidor. Severidad media si esto fuera producción. Aquí es el contrato
publicado, así que no rompe el caso del enunciado.

OBS-02. Alta, cambio y borrado no piden autenticación.
Cualquiera con la URL puede crear, modificar o borrar. En la demo es el
comportamiento publicado. En una tienda real bloquearía la salida.

OBS-03. La búsqueda por estado no está paginada.
En esta corrida findByStatus?status=sold devolvió 417 mascotas de todos
los que usan la demo, no solo la nuestra. La prueba encontró la suya, pero
la lista es compartida y crece. En una API real haría falta paginación y
un dueño del dato. No se midió carga: 417 registros respondieron en 328 ms
esta vez, y eso no es un umbral.


4. Herramienta

Las llamadas son cy.request contra la base /v2. No hay pantalla que
